# perf — Mojaloop load generation and measurement

Drives transfer load through DFSP SDK scheme-adapter outbound APIs and
measures what a payer actually experiences. Requirements and the reasoning
behind each design decision are in [REQUIREMENTS.md](REQUIREMENTS.md).

```
make perf-seed  ENV=<env>                     register + verify test parties
make perf-check ENV=<env>                     readiness gate (needs a kubeconfig)
make perf-run   ENV=<env> SCENARIO=<name>     run a scenario
make perf-index                               regenerate INDEX.md
```

Needs `k6`, `yq` and `jq`. Cluster access is optional and used only by
`perf-check` and post-run health recording — load generation never needs it.

## Getting started

```bash
cd environments/<env>
cp ../mlf-lab1-sw1/perf-topology.yaml.sample perf-topology.yaml
mkdir -p perf-scenarios
cp ../mlf-lab1-sw1/perf-scenarios/smoke.yaml.sample perf-scenarios/smoke.yaml
cp ../mlf-lab1-sw1/perf-scenarios/baseline-1tps.yaml.sample perf-scenarios/baseline-1tps.yaml
```

1. Edit `perf-topology.yaml` — replace every `CHANGEME`. Each participant needs
   five complete URLs; nothing is derived from a hostname pattern or an id.
2. Edit the scenarios — replace the participant ids in `pairs`.
3. `make perf-seed ENV=<env>` — registers each participant's MSISDN range and
   verifies a sample resolves through the ALS.
4. `make perf-run ENV=<env> SCENARIO=smoke` — 30 seconds, proves the chain
   works before you spend half an hour on a soak.
5. `make perf-run ENV=<env> SCENARIO=baseline-1tps` — the reference run.

## What a run measures

Each iteration is three separately-timed calls, so latency is attributable to
a phase rather than landing in one aggregate number:

```
GET  {discovery}/MSISDN/<id>   discovery_time
POST {quotes}                  quote_time
POST {transfers}               transfer_time     ilpPacket + condition from the quote
                               e2e_time = total
```

The generator runs locally, so **the network path from your machine to the
participants is inside every latency figure**. Compare runs with each other;
treat absolute values with care.

## Reading a result

```
compliance (counted exactly, not interpolated)
  within  0.5s      0.000%
  within    1s      0.000%
  within    5s     93.103%  <- gate
```

**Compliance is the gate, not the percentile.** Percentiles are reported too,
but a percentile sitting near a threshold is interpolated inside whatever
bucket spans it. Compliance is a count taken as each transfer finishes, so it
is exact. The thresholds match the bucket boundaries used by `moja_*`,
`mojaloop_connector_*` and `traces_span_metrics_*`, which is what lets you
compare client-side compliance against hub-side compliance at the same value.

Three things to check before believing any number:

- **`dropped` in the output or the index.** The generator could not offer the
  load the scenario asked for. Whatever it measured, it was not that load.
- **`HEALTH: TAINTED`.** Pods restarted during the run. Per-process counters
  reset on restart, so anything derived from them understates.
- **`HEALTH: not observed`.** No cluster access, so nothing is known about
  what the system was doing.

A run that fails its SLO exits non-zero. That is a result, not an error.

## Layout

Configuration lives with the environment it belongs to. Code lives here.
Results live on their own, so they survive the environment being rebuilt.

```
perf/                                   CODE ONLY — tracked
  bin/                                  resolution and orchestration
  k6/                                   the load and seeding scripts
  INDEX.md                              generated by make perf-index
  RESULTS.md                            frozen archive of the previous campaign

environments/<env>/                     CONFIG — gitignored, like config.yaml
  perf-topology.yaml                    WHERE the participants are
  perf-scenarios/<name>.yaml            WHAT to run: rate, pairs, thresholds

environments/mlf-lab1-sw1/              the tracked samples to copy from
  perf-topology.yaml.sample
  perf-scenarios/*.yaml.sample

perf-result/<env>/<scenario>/<ts>/      RESULTS — committed
  summary.json                          machine-readable results
  scenario-snapshot.yaml                the test as run, overrides applied
  health.json                           restarts, OOM kills, taint
  deployment/                           what was deployed while it ran
    config.yaml                         sizing profile, artifact version, data modes
    values/*.yaml                       Helm value overrides, verbatim
    patches/*.yaml                      kustomize patches, verbatim
  notes.md                              yours to write
```

**A result records what was running, never where it was.** Endpoints,
hostnames, VIPs, registry and storage addresses and credentials stay out —
those belong to `environments/<env>/perf-topology.yaml` and `config.yaml`, and
are managed like any other deployment config. So a result is reproducible only
if you also hold that config, which is the same property `make plan-apply`
has, and it is why results can be committed without publishing your
infrastructure.

## What was deployed

Every run copies the deployment's inputs beside its numbers, because
`environments/<env>/` is gitignored and none of it is recoverable afterwards.
Without it a result is a number with no subject: two runs a fortnight apart
cannot be compared, and the change you were testing went unrecorded.

Captured from the environment's own files — never from the cluster, so this
works with no kubeconfig and cannot fail a run:

| Captured | From |
|---|---|
| `deployment/values/*.yaml` | `environments/<env>/values/*.yaml` |
| `deployment/patches/*.yaml` | `environments/<env>/patches/*.yaml` |
| `deployment/config.yaml` | `config.yaml`, six keys only: `.version` `.template` `.infra` `.artifact` `.data` `.app.api_type` |

`diff -r` between two results' `deployment/` directories is the change
between those two runs.

Two things this does not do. It records the **files**, not the cluster — so
`make apply-config` before you measure, or you will record a values file the
deployment never saw. And it captures values and patches in their **authored**
form; `${...}` template variables are substituted at deploy time from
`config.yaml` and the sizing profile, both of which are captured alongside.

## Overrides

Any scenario value can be overridden per invocation:

```bash
make perf-run ENV=<env> SCENARIO=baseline-1tps TPS=5 DURATION=10m
make perf-run ENV=<env> SCENARIO=ramp-to-slo STEPS=1,5,10,20 STEP_DURATION=3m
```

`TPS DURATION WARMUP STEPS STEP_DURATION SHAPE CURRENCY AMOUNT
REQUEST_TIMEOUT SLO_TARGET TRACE_SAMPLE_MS`

Overrides are resolved before k6 starts and written into
`scenario-snapshot.yaml`, so a run reproduces from its result rather than from
your shell history.

## Telemetry

Declared in `environments/<env>/perf-topology.yaml`, because where telemetry
goes is a property of the environment, not of a test:

```yaml
observability:
  metrics_url: https://<remote-write-host>/api/v1/receive
  logs_url:    https://<loki-host>/loki/api/v1/push
  traces_url:  https://<tempo-host>/v1/traces
  insecure_skip_tls_verify: false
```

Override per invocation with `PERF_METRICS_URL` / `PERF_LOGS_URL`. Omit the
block entirely and runs still produce a full result — only the live dashboards
go dark. **Log shipping is opt-in via `SHIP_LOGS=1`**: k6 accepts a single log
destination, so sending logs to Loki silences your terminal.

Results record *whether* each signal was shipped, never the URL — endpoint
addresses stay in the environment's config.

**The three signals are not symmetric, and the difference matters:**

| Signal | What happens |
|---|---|
| Metrics | k6 pushes its own metrics via remote-write, tagged `testid=<run id>` |
| Logs | k6 pushes its own run logs to Loki, labelled `testid`, `scenario`, `topology` |
| Traces | **k6 pushes nothing.** It injects a `traceparent`; the spans are produced by the hub and DFSP services and collected by *their* agents |

`traces_url` exists so a report can link to where its traces landed. Setting
it exports nothing. If traces are missing, the gap is in the services'
instrumentation or their collectors — not here.

Metric series are tagged by `phase`, `source` and `dest`. Compliance arrives
as `k6_within_slo_rate{threshold="1"}`, using bare threshold values (`1`,
`0.5`) so one dashboard variable can drive both client-side and hub-side
panels.

## Things that will bite you

- **`yq` loses integer precision at MSISDN magnitudes.** It evaluates
  `20100009003 - 20100009001 + 1` as `1`. Use `jq` for any arithmetic on
  identifiers; `yq` is for reading fields only.
- **Size MSISDN ranges deliberately.** Too small and identifiers recur within
  a run, producing cache-level contention and failures that have nothing to do
  with the system under test.
- **`request_timeout` should sit well above the realistic worst case.** Too
  tight and ordinary slowness is recorded as failure, which aborts runs for
  the wrong reason.
- **`traceparent` is injected; `tracestate` deliberately is not.** Setting one
  risks displacing the Mojaloop Event SDK's own vendor entry, which carries
  the timestamps some hub metrics are derived from.
